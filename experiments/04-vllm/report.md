# 04-vllm

상태: 1차 측정 완료 (2026-10-29, RunPod RTX 6000 Ada + vLLM 0.32.0)

## 목적

Mac + Ollama에서 한 실험을 NVIDIA GPU + vLLM에서 같은 측정 도구로 반복한다. 측정 전에 Mac에서 세운 모델(메모리 대역폭, prefill 연산량)로 결과를 예측하고, 예측과 실측을 비교한다.

- 실행 계획과 명령: [plan.md](plan.md)
- 환경: [환경 기록](../../docs/environment.md)의 GPU 서버 2026-10-29 항목
- 측정 도구: [`benchmark/ttft.py`](../../benchmark/ttft.py) `--api openai`, [`workloads/prefix_variants.py`](../../workloads/prefix_variants.py)

## 공통 조건과 Mac 비교 시 주의

- GPU: RTX 6000 Ada 1장, 측정 스크립트는 같은 Pod 안에서 실행
- 모델: `meta-llama/Llama-3.1-8B-Instruct` bf16 (약 16.1 GB). Mac은 같은 모델의 Q4_K_M(약 4.92 GB)이다. **양자화가 다르다.**
- 서버: `--max-model-len 4096 --gpu-memory-utilization 0.90`, prefix caching 기본 켜짐
- 요청: OpenAI 호환 `/v1/chat/completions`, temperature 0, seed 42
- **입력 토큰 수 차이:** vLLM은 Hugging Face의 Llama 3.1 chat template을 쓰며 system 헤더(날짜 정보)를 붙여 같은 질문이 약 25 tokens 길다(예: 숫자 세기 질문 Mac 39, vLLM 64). 짧은 입력에서는 TTFT 차이에 거의 영향이 없다. 이 공통 헤더 때문에 서로 다른 요청끼리도 prefix cache가 일부 재사용됐다(서버 로그의 hit rate 약 35%).
- 조건당 1~3회 측정했다.

## 서버 메모리 배분 (서버 로그)

| 항목 | 예측 | 실제 |
| --- | ---: | ---: |
| 모델 가중치 | 약 16 GB | 15.0 GiB (= 16.1 GB) |
| KV cache 공간 | 25~28 GB | 25.95 GiB |
| KV cache 토큰 수 | 20만~22만 | 212,576 |
| 4096 tokens 요청 동시 수용 | 약 53 | 51.9 |

- 25.95 GiB ÷ 212,576 tokens = 128 KiB/token. llama3.1 8B의 토큰당 KV cache(32 layers × 8 KV heads × 128 dim × K·V × 2 bytes)와 정확히 같다.
- 예측보다 KV cache가 작은 것은 활성값 1.43 GiB, CUDA graph 0.24 GiB가 빠졌기 때문이다.
- vLLM은 KV cache를 16 tokens 블록 단위로 필요한 만큼 나눠 쓴다(PagedAttention). Ollama처럼 처리 칸마다 context 길이만큼 미리 잡지 않는다.

## 실험 1: 단일 요청

결과: `results/single/` (3회)

| | Mac (Ollama, Q4) | vLLM (bf16) | 예측 |
| --- | ---: | ---: | ---: |
| TPOT | 18.3 ms | 17.84~17.86 ms | 18.6 ms |
| TTFT | 약 103 ms | 45~50 ms | Mac보다 짧음 |

- 예측: `TPOT ≈ 16.1 GB ÷ (960 GB/s × 0.9) ≈ 18.6 ms`. GPU 대역폭이 약 3배지만 bf16 모델도 약 3배라 Mac과 비슷할 것으로 봤고, 그대로 나왔다.
- 부하 중 메모리 클럭은 9,501 MHz였다(사양 최대 10,001 MHz). 실제 대역폭은 9,501 × 2 × 384 ÷ 8 ≈ 912 GB/s다. 토큰마다 읽는 양은 입력 임베딩 표(약 1 GB)를 빼면 약 15 GB이므로, 15 GB ÷ 17.9 ms ≈ 838 GB/s로 실제 대역폭의 약 92%를 썼다. Mac(85~90%)과 비슷하다.

## 실험 2: 입력 길이

결과: `results/input-length/` (길이마다 3회, 매번 맨 앞 번호로 cache 회피)

| 입력 (Mac / vLLM tokens) | Mac TTFT | vLLM TTFT 3회 (ms) | vLLM 중앙값 | 단축 |
| --- | ---: | --- | ---: | ---: |
| 40 / 65 | 110 ms | 54 / 47 / 48 | 48 ms | 2.3배 |
| 130 / 155 | 124 ms | 51 / 46 / 47 | 47 ms | 2.6배 |
| 530 / 555 | 505 ms | 93 / 89 / 88 | 89 ms | 5.7배 |
| 1030 / 1055 | 953 ms | 132 / 144 / 152 | 144 ms | 6.6배 |
| 2030 / 2055 | 1992 ms | 265 / 288 / 287 | 287 ms | 6.9배 |

- 예측(2000 tokens에서 0.2~0.5초)과 맞았다.
- 555 → 2055 tokens 구간에서 토큰당 약 0.13 ms, 입력 처리 속도 약 7,600 tok/s(Mac 약 1,030 tok/s). 연산량으로 약 7,600 × 16 GFLOP ≈ 120 TFLOPS(Mac 약 16.5 TFLOPS).
- TPOT은 17.5 → 18.2 ms로 약 4% 늘었다. Mac(약 7%)보다 작다. bf16 가중치가 커서 KV cache가 차지하는 비중이 상대적으로 작기 때문이다(0.27 GB ÷ 16 GB vs 0.27 GB ÷ 4.9 GB).
- 해석: decode(TPOT)는 메모리 대역폭 대 모델 크기 비율이 같아 Mac과 같았고, prefill(TTFT)은 연산 능력 차이만큼 약 7배 빨랐다. "decode는 메모리, prefill은 연산이 병목"을 두 하드웨어 비교로 확인했다.

## 실험 3: 출력 길이와 GPU 상태

결과: `results/output-length/` (길이마다 3회), `results/output-length-gpu.csv` (1초 간격)

| 출력 tokens | 예측 (TTFT + N × 17.8 ms) | 실제 3회 | TPOT 3회 |
| ---: | ---: | --- | --- |
| 16 | 약 0.33 s | 0.32 / 0.32 / 0.31 s | 17.8 ms |
| 64 | 약 1.19 s | 1.17 / 1.17 / 1.17 s | 17.8 ms |
| 256 | 약 4.6 s | 4.60 / 4.60 / 4.60 s | 17.9 ms |
| 1024 | 약 18.3 s | 18.36 / 18.37 / 18.37 s | 17.9 / 17.9 / 17.9 ms |

1024 tokens 3회 연속 실행 중 GPU 상태:

| 항목 | 유휴 | 실행 중 (약 75초) |
| --- | --- | --- |
| SM 클럭 | 210 MHz | 2,730 → 2,595 MHz (약 5% 하락) |
| 메모리 클럭 | 405 MHz | 9,501 MHz 고정 |
| 전력 | 약 20 W | 약 300 W (한도 300 W) |
| 온도 | 27 °C | 최대 55 °C |
| GPU-Util | 0% | 100% |

- Mac은 같은 조건에서 TPOT이 18.6 → 20.0 ms로 회차마다 늘었으나 vLLM은 3회 모두 17.9 ms였다.
- SM 클럭이 조금 내려간 원인은 온도(55 °C)가 아니라 전력 한도로 본다. decode는 메모리 대역폭에 묶여 있고 메모리 클럭이 고정이라 TPOT에 영향이 없었다.
- GPU-Util 100%는 GPU가 무언가를 실행 중인 시간 비율이지 연산 사용률이 아니다. 대부분은 메모리를 기다리는 시간이다.
- 에너지: 사용자 1명 생성 시 Mac 약 28 W / 56 tok/s ≈ 0.5 J/token, GPU 약 300 W / 56 tok/s ≈ 5.4 J/token. 혼자 쓰면 GPU가 10배 이상 비효율적이다.

## 실험 4: 동시 사용자

### (a) 기본 설정에서 사용자 수 증가

결과: `results/concurrency-default-{8,16,32,64,128,256}req-*/`. 질문은 숫자 세기, 출력 64 tokens, 요청마다 맨 앞 번호가 다르다.

| 동시 사용자 | TTFT 평균 / p95 | TPOT 평균 / p95 | 목표 충족 | 한 단계 처리량 |
| ---: | --- | --- | ---: | ---: |
| 1 (실험 1) | 48 ms | 17.8 ms | 1/1 | 56 tok/s |
| 8 | 89 / 92 ms | 18.2 / 18.2 ms | 8/8 | 440 tok/s |
| 16 | 102 / 108 ms | 18.5 / 18.9 ms | 16/16 | 866 tok/s |
| 32 | 147 / 185 ms | 19.6 / 20.2 ms | 32/32 | 1,634 tok/s |
| 64 | 327 / 403 ms | 22.0 / 23.7 ms | 64/64 | 2,908 tok/s |
| 128 | 629 / 760 ms | 27.5 / 31.1 ms | 127/127 | 4,621 tok/s |
| 256 | 1,177 / 1,384 ms | 47.9 / 58.4 ms | 4/256 | 5,345 tok/s |

- 목표: TTFT 1초 이내, TPOT 50 ms 이내. 한 단계 처리량 = 사용자 수 ÷ 평균 TPOT.
- 128명까지 전원 목표를 지켰고 256명에서 TTFT와 TPOT이 함께 목표를 넘었다. 이 장비에서 목표를 지키는 동시 사용자는 128~256명 사이다. Mac + Ollama는 약 4명이었다.
- 128명 실행에서 결과 파일이 127개다. 서버 로그로 요청 535개가 모두 200 OK였음을 확인했다. 동시에 띄운 두 프로세스의 파일 이름(마이크로초 시각)이 겹쳐 덮어쓴 것으로, 이후 `ttft.py`가 파일 이름에 프로세스 번호를 붙이도록 고쳤다.

### Mac과 비교 (사용자 8명)

| 동시 처리 수 | Mac TPOT | vLLM TPOT | Mac 마지막 TTFT | vLLM 마지막 TTFT |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 18.2 ms | 17.9 ms | 8.82 s | 8.13 s |
| 2 | 24.9 ms | 18.1 ms | 5.24 s | 3.58 s |
| 4 | 35.0 ms | 18.1 ms | 2.65 s | 1.24 s |
| 8 | 62~65 ms | 18.1 ms | 0.42 s | 0.09 s |

### 해석

- 묶음 처리 효율: 이상적이라면 묶어도 한 단계 시간이 그대로여서 처리량이 사용자 수에 비례한다. vLLM 64명은 한 단계가 17.8 → 22.0 ms(1.24배)로 이상 대비 약 81%였다. Mac 8명은 17.8 → 61.7 ms(3.5배)로 약 29%였다. 사용자 한 명을 더할 때 늘어나는 한 단계 시간은 vLLM 약 0.07 ms, Mac 약 5~7 ms다.
- Mac에서 "묶음 생성의 추가 비용은 GPU 연산 한계가 아니라 llama.cpp 구현 효율 때문일 수 있다"는 가설을 세웠고, vLLM 결과는 이를 뒷받침한다. 다만 하드웨어(연산 능력 약 7배)도 달라 엔진 차이와 하드웨어 차이가 섞여 있다. 분리하려면 같은 GPU에서 Ollama를 측정해야 한다.
- 메모리 병목에서 연산 병목으로 넘어가는 지점(roofline): bf16은 가중치 1 byte를 읽을 때 사용자 1명당 연산 1회를 한다. GPU가 1 byte를 읽는 동안 할 수 있는 연산은 약 120 TFLOPS ÷ 0.9 TB/s ≈ 130회다. 따라서 약 130명까지는 메모리 병목이고 그 이상은 연산 병목으로 예측된다. 실제로 128명까지 TPOT이 완만히 늘다가 256명에서 47.9 ms로 급증했다(그때 연산량 약 5,345 tok/s × 16 GFLOP ≈ 85 TFLOPS). 연산 성능은 prefill 측정값으로 근사했다.
- 256명의 TTFT 약 1.2초(최대 1.5초)는 몰린 입력 처리로 설명된다. 요청당 입력은 65 tokens지만, 앞쪽 약 30 tokens(system 헤더와 `[req`)는 모든 요청이 같아 prefix cache로 재사용된다. 새로 계산할 양은 약 256 × 35 ≈ 9,000 tokens이고, 실험 2의 입력 처리 속도(약 7,600 tok/s)로 약 1.2초다. 대화 중에는 256명 × 40 tokens로 계산했으나 실제 입력 토큰 수(65)와 공통 앞부분 재사용을 반영해 고쳤다.
- 동시 처리 수 제한: Mac에서는 동시 처리 수가 TTFT와 TPOT을 맞바꾸는 설정이었으나, vLLM에서는 1~8 범위에서 TPOT이 그대로라 제한할수록 대기만 길어졌다. TTFT·TPOT trade-off는 항상 있지만 시작 지점(메모리 병목이 끝나는 지점)이 하드웨어와 엔진에 따라 크게 다르다. 설정값은 환경마다 측정해서 정해야 한다.
- 비용: 64명 부하에서 약 2,900 tok/s, 300 W → 약 0.1 J/token. 혼자 쓸 때(5.4 J/token)보다 수십 배 효율적이다. 출력 100만 tokens당 약 $0.99 ÷ (2,900 × 3,600 ÷ 10⁶) ≈ $0.1 수준이다(부하가 계속 유지된다는 가정).

## 실험 5: Prefix cache (바뀐 위치)

결과: `results/prefix-change{none,0,25,50,75,100}-rep{1,2,3}/`. 02-prefix-cache 실험 2와 같은 입력(약 1,050 tokens 문서)이다.

| 바뀐 위치 | Mac B 평균 | vLLM 예측 | vLLM B 3회 (ms) | vLLM B 평균 |
| ---: | ---: | ---: | --- | ---: |
| 바꾸지 않음 | 112 ms | 약 48 ms | 49 / 46 / 48 | 48 ms |
| 0% | 954 ms | 약 144 ms | 144 / 139 / 143 | 142 ms |
| 25% | 740 ms | 약 120 ms | 109 / 110 / 107 | 109 ms |
| 50% | 516 ms | 약 95 ms | 83 / 77 / 84 | 81 ms |
| 75% | 351 ms | 약 72 ms | 67 / 69 / 62 | 66 ms |
| 100% | 115 ms | 약 48 ms | 52 / 46 / 47 | 48 ms |

cache 없는 A 요청은 121~168 ms였다.

- 원리는 llama.cpp와 같다. 처음부터 같은 부분까지만 재사용하고, 맨 앞이 바뀌면 재사용이 전혀 되지 않았다. 프롬프트 설계 규칙(고정된 내용은 앞, 바뀌는 내용은 뒤)이 vLLM에도 그대로 적용된다.
- 중간 위치는 직선 예측보다 10~15 ms 빨랐다. 입력 처리 시간이 토큰 수에 완전히 비례하지 않는 것으로 보이며 원인은 확인하지 않았다.
- 재사용으로 아낀 시간은 Mac 약 842 ms, vLLM 약 94 ms다. 빠른 GPU에서는 1,000 tokens를 다시 계산해도 0.1초라 짧은 문서의 cache 가치가 작다. cache는 문서가 수만 tokens이거나, 사용자가 많아 prefill이 몰릴 때 더 중요해진다.

## 결론

1. Mac에서 세운 메모리 대역폭 모델로 처음 쓰는 GPU의 TPOT을 측정 전에 약 5% 오차로 예측했다.
2. decode 속도는 "메모리 대역폭 ÷ 모델 크기"가, prefill 속도는 연산 능력이 정한다. 두 장비 비교에서 각각 확인했다.
3. vLLM은 묶음 처리 효율이 높아(64명에서 이상 대비 81%) 동시 128명까지 목표를 지켰다. Mac + Ollama는 약 4명이었다.
4. TTFT·TPOT trade-off는 메모리 병목이 끝나는 지점(이 GPU에서 약 130명)부터 나타난다. 그 아래에서는 동시 처리 수를 제한할 이유가 없다.
5. prefix cache의 원리와 설계 규칙은 엔진과 무관하게 같고, 체감 효과는 prefill 속도에 따라 달라진다.

## 한계와 다음

- 모델 양자화(Q4 vs bf16)와 chat template(약 25 tokens 차이)이 Mac과 다르다.
- 엔진 차이와 하드웨어 차이를 분리하지 않았다. 같은 GPU에서 Ollama 또는 같은 양자화 모델로 비교할 수 있다.
- 동시 사용자 실험은 모든 요청이 같은 순간에 도착한다. 실제 서비스처럼 시간차를 두고 계속 도착하는 부하(요청 도착률)로 측정하지 않았다.
- 사용자 수별 1회씩만 측정했다.
- 기본 설정 동시 사용자 실험의 GPU 기록은 이후 기록이 같은 파일 이름을 덮어써 남지 않았다. `results/concurrency-gpu.csv`는 13:50 이후(동시 처리 수 8 실험)만 담고 있다.
- seqs4, seqs8 서버 로그는 보관하지 않았다. 측정 결과 JSON은 모두 있다.
- prefix caching을 끈 대조 실험(`--no-enable-prefix-caching`)은 하지 않았다.
- 다음 후보: FP8 양자화 비교(이 GPU는 FP8 지원), 요청 도착률 기반 부하, `vllm bench serve`와 직접 만든 도구 비교, 긴 문서(수만 tokens)에서 prefix cache 효과.
